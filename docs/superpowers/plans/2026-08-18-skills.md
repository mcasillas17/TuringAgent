# Skills Implementation Plan

> Historical record of the database-backed, per-conversation design shipped in
> #45. It is superseded by `2026-08-18-skills-as-files.md`; current skills are
> file-backed, model-selected, and not attached to conversations.

Written after the fact. Skills shipped in #45 without a plan, and the four
sections built alongside it — Agents, Integrations, Automations, Telemetry —
were implemented in parallel by people who could not see each other's work.
This records what was decided and why, and names the composition questions
nobody answered at the time. Two of those turn out to have answers already
baked into the code that nobody chose deliberately; they are in **Open
questions**, not presented as design.

## What a skill is

A named block of instructions the user writes once and attaches to the
conversations where it applies. "Answer in short sentences." "When I ask about
invoices, check the sandbox first."

## Design decisions (locked)

**Attachment is by hand, never inferred.** The user was asked directly and
chose named instructions attached per chat over always-on rules and over
model-selected relevance. A conversation follows exactly the skills someone
attached to it. This is the property that makes a surprising answer traceable
to one named skill instead of to a selection step nobody can inspect.

**Titles derive from the user's words, not the model.** A skill's *name* is
whatever the user typed. Nothing summarises it. Summarisation would cost a
round trip, and could hallucinate a name for a rule the user has to trust.

**Instructions are frozen into the job at enqueue.** `attachedSkillsTx` runs
inside the same transaction that queues the run
(`repository/jobs.go`), so editing or detaching a skill cannot reach back into
a reply already being generated. The user pressed send on the instructions as
they were at that moment.

**Deleting a skill detaches it everywhere,** via `ON DELETE CASCADE`. A skill
that no longer exists must not keep instructing conversations. Runs already
queued are unaffected, because of the snapshot above — the delete dialog says
both of these things.

**Names are unique, case-insensitively.** The name is how a user refers to a
skill and how the runtime attributes an instruction back to one. Two skills
sharing a name makes both ambiguous.

**Skill text is treated as data, not as prompt.** It is user-authored but not
necessarily user-written — it is exactly the kind of thing someone pastes from
a template. So names are flattened to a single line (a newline in a name would
otherwise open a second `##` section and impersonate a skill that was never
attached), and the "your latest message wins" rule is restated *after* the
bodies as well as before, so a body ending in "ignore the above" is not the
last word.

**This is not a security boundary, and the code says so.** What stops a skill
causing a mutation the user did not approve is the approval token mcp-files
demands, not wording in a prompt. Anyone strengthening the prompt should not
believe they are strengthening a control.

**Sizes are bounded in the repository, not the editor.** Name 120 runes,
instructions 8000. The full text is copied into `jobs.payload_json` for every
message in a conversation using it, and into every request to a model with a
finite context. The editor is one client of several.

## What review caught, kept here so it is not re-learned

- The job payload's skill keys had no `json` tags. Adding them later would
  have silently decoded every already-queued job's skills to empty strings.
  The tags are load-bearing and commented as such.
- Attaching to a deleted conversation reported a missing **skill**, sending the
  user to look in the wrong place. The repository now probes which side is
  actually missing.
- The per-conversation skills bar could show the previous conversation's set
  while the new one loaded. It is keyed by session id.
- A failed toggle raised a snackbar *underneath* the modal sheet, so the tick
  simply did not move and the user was told nothing.
- A failed read rendered "No skills attached" — a confident claim about state
  that had just failed to load.

## Prior art, and where we deliberately differ

Checked against primary documentation rather than recollection, because the
three systems people compare this to all made the *same* choice, and we made a
different one.

| | OpenClaw | Hermes | Scout | **TuringAgent** |
|---|---|---|---|---|
| Unit | `SKILL.md` + YAML frontmatter | `SKILL.md`, agentskills.io standard | `SKILL.md` | row in SQLite |
| Lives in | skills directory + ClawHub registry | `~/.hermes/skills/` | skills directory | the database |
| Chosen by | the model, by intent (default) | slash command, conversation, or the agent itself | not stated first-party | **the user, by hand** |
| Explicit invoke | `$skill-name` | `/skill-name`, up to 5 leading tokens | not stated first-party | attach to a conversation |
| Scope | agent-level allowlists; **no per-conversation scoping** | session; project-local skills for a repo | not stated first-party | **per conversation** |
| Loading | snapshot at session start | progressive disclosure: `skills_list()` ≈3k tokens, then `skill_view(name)` | not stated first-party | full text of every attached skill, every message |

Confidence: OpenClaw and Hermes rows are from their own docs. Scout's format
row is first-party — *"You can also create your own custom skills by placing
`SKILL.md` files in your skills directory"* — but Microsoft's public docs do not
describe invocation or scoping, so those cells say so rather than guess. That
ClawPilot was Scout's internal codename comes from secondary reporting only.

**What our difference buys.** Explicit per-conversation attachment means what a
conversation follows is exactly what someone attached to it. There is no
selection step to debug, and a surprising answer is traceable to one named
skill. That is the property the user picked when asked, and it is the reason
the library is small and hand-curated rather than a registry.

**What it costs, and this is not hypothetical.** Two things:

1. **It does not scale past a handful.** ClawHub carries thousands of skills;
   nobody hand-attaches from thousands. Our model assumes a personal library of
   a few.
2. **Every attached skill's full text goes into every message.** Hermes'
   progressive disclosure exists precisely to avoid this: it spends ~3k tokens
   listing names and descriptions, and only loads a body when the skill is
   actually used. We spend the whole body every turn. With an 8000-rune cap and
   a local 7B model, three or four attached skills is a real share of the
   context window — and now that Telemetry reports token counts, this is
   measurable rather than theoretical.

**One thing worth stealing.** Hermes' `requires_toolsets` is a *visibility
filter, not an access control* — their docs are explicit that nothing stops a
skill calling a tool it did not declare. Our Automations allowlist is the
opposite: enforced, and the enforcement is the point. Worth keeping the
distinction sharp if skills ever grow a tool declaration, because the same
field name in two systems meaning two different things is how a safety
assumption gets imported by mistake.

**Not adopted, and why.** `SKILL.md` files would give git versioning, sharing,
and editing in a real editor — genuinely better ergonomics for a local-first
tool, and the interop path if agentskills.io matters later. We store rows
instead because attachment is per conversation and the join lives in the same
database as the conversations. Revisit if a skill library ever wants to be
shared or reviewed.

## Open questions — behaviour that exists but was never designed

These are real today. Each is defensible; none was chosen.

**1. Skills are sent to external agents.** `general_assistant.go` applies the
skills system message before the routed/local distinction matters, so routing a
conversation to Claude or GPT sends its attached skill text off the machine.

Recall is explicitly skipped for routed runs, and the picker says so. The
asymmetry is arguably right — recall draws on *other* conversations the user
never chose to send, while skills belong to *this* conversation, which the user
did opt into routing. But it is undisclosed: the Agents work made a point of
naming what leaves the machine and did not mention skills. **Recommendation:**
say it where routing is chosen, in the same place the recall exclusion is said.

**2. Automation runs inherit the conversation's skills.**
`repository/automations.go` enqueues through `enqueueUserMessageTx`, which
snapshots attached skills like any other message. So a scheduled, unattended
run follows whatever skills are attached to its conversation.

Also defensible — it is that conversation, with its instructions. But combined
with a per-automation tool allowlist, a skill can direct the agent's use of a
pre-approved tool at a time nobody is watching, and the automation editor never
mentions skills. **Recommendation:** show the attached skills in the automation
editor beside the allowlist, so the whole of what will run unattended is on one
screen.

**3. Telemetry does not attribute anything to skills.** There is no measure of
which skills are attached to the most conversations, or whether runs carrying a
given skill use more tokens. The data exists — the snapshot is in every job
payload. Not built, and not obviously worth building until someone wants it.

## Verification (as shipped)

Repository CRUD, attach/detach idempotency, the delete cascade, the payload
snapshot surviving an edit and a detach, and rejection of duplicate names.
`skillsSystemMessage` rendering, including the heading-forgery and
precedence-restatement cases. The `Execute` path, proving the system message
reaches the model ahead of the conversation and is absent when nothing is
attached. Service-layer error-code mapping. Flutter coverage of the library,
the editor, the per-conversation bar and the picker, including failure and
empty states.

The load-bearing tests were checked for discrimination by breaking the
production code and confirming the intended test failed.
