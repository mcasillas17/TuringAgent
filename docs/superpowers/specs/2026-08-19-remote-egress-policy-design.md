# Remote Provider Egress Policy Design

**Status:** approved for TUR-003 implementation on 2026-08-19.

## Purpose

Turing must not send conversation, recall, memory, skills, tool data, or
attachments off-machine merely because a remote provider happens to be
configured. Every interactive remote run needs a fresh disclosure and consent
decision bound to the exact request and destination. Local failures and
background work remain local.

The orchestrator owns this policy. Flutter renders the disclosure and returns
the user's decision. The runtime receives a frozen run decision and verifies it
before provider I/O. Neither client nor runtime can mint or broaden consent.

## Scope

This change covers both existing remote execution paths:

1. the OpenAI-compatible model provider selected on `SendMessage`; and
2. a session routed to a configured external agent.

Ollama remains the local path. Memory/profile context and attachments are not
implemented today, so this change defines their typed categories but never
claims or sends them. No standing remote policy, background remote execution,
or per-session consent is introduced.

## Data-category model

`EgressDataCategory` is a closed protobuf enum:

- current message;
- conversation history;
- cross-session recall;
- memory/profile;
- skill content;
- tool schemas;
- tool arguments;
- tool results; and
- attachments.

A disclosure is the conservative maximum that may cross the boundary for one
prepared send. Runtime use may be a subset, never a superset. Direct
OpenAI-compatible runs disclose current message, history, possible recall,
eligible skill content, and tool schemas/arguments/results. Routed external
agents disclose the same set except recall, which their current execution path
already suppresses. Unsupported memory/profile and attachments are absent.

Adding an applicable category is a request-context change and requires another
prepare/confirm cycle.

## Prepare and consent protocol

`ChatService.PrepareRemoteEgress` accepts the same bounded, normalized
payload-shaping and routing fields as `SendMessage`, including the idempotency
key. Its exact value is bound even when an API caller deliberately leaves it
empty; the official Flutter client always supplies one. The RPC:

1. validates every identifier, collection, count, and content bound;
2. resolves the effective provider/model/agent/endpoint;
3. freezes the currently selected tool names;
4. reads the eligible skill snapshot and hashes its canonical representation;
5. records whether recall and memory/profile are applicable;
6. computes sorted disclosure categories;
7. creates a random nonce and short expiry;
8. creates a versioned canonical request-context fingerprint; and
9. returns a signed challenge plus destination and categories.

Preparing is read-only. It creates no session, message, run, job, event, audit
row, challenge row, or log containing request content.

The challenge is HMAC-SHA256 signed with dedicated
`TURING_EGRESS_SIGNING_SECRET` key material held only by the orchestrator.
Derivation/signing uses the fixed domain `turing.remote-egress.challenge.v1`.
The secret is generated by backend initialization, passed only to the
orchestrator, never persisted, and never sent to Flutter or the runtime. It is
independent of the public client bearer key and service-identity credentials,
so TUR-006 can change internal identities without changing this boundary.

The signed canonical payload binds:

- format version;
- session ID;
- idempotency key;
- digest of the exact normalized message/request payload;
- effective provider, model, external-agent identity, canonical endpoint, and
  non-secret credential-reference digest;
- selected tool names;
- canonical eligible-skill snapshot digest;
- absence/presence of attachment selection;
- recall and memory/profile applicability flags;
- sorted disclosure categories;
- nonce; and
- expiry.

Unknown fields, duplicate or unsorted categories, invalid enum values,
noncanonical endpoint text, excessive lengths/counts, and trailing challenge
data are rejected. The raw message and request payload are hashed, not embedded
in the challenge.

`SendMessage` carries `RemoteEgressConsent`: the challenge, an explicit
acknowledgment boolean, and the exact categories acknowledged. Missing or false
acknowledgment fails before persistence.

## Idempotency and one-time use

An exact TUR-001 replay is special because the run and consent decision already
exist. `SendMessage` therefore:

1. verifies and canonically decodes the signed challenge without applying its
   expiry or nonce-use checks;
2. computes the same versioned enqueue fingerprint from the request and signed
   context;
3. looks up the idempotency key;
4. returns the original run and decision when the fingerprint matches, even
   after challenge expiry or later routing/configuration changes;
5. returns the existing deterministic idempotency conflict when it differs;
6. only for a new operation, validates expiry, current effective route,
   categories, tools, skills, recall/memory flags, and nonce availability; and
7. enqueues atomically.

The durable decision table has a unique nonce and a unique run ID. Two
concurrent requests with one challenge can create only one decision. Calls with
the same idempotency key replay the same run; a different idempotency key using
the consumed nonce fails deterministically. Assignment retries of the same
frozen job retain the existing decision and do not consume new consent.

## Durable model and transaction boundary

`run_egress_decisions` is one-to-one with `agent_runs` and uses
`ON DELETE CASCADE`. It stores:

- decision ID and version;
- run ID;
- unique challenge nonce;
- versioned request-context fingerprint;
- provider and model;
- external-agent identity when applicable;
- exact canonical endpoint plus a separately bounded host;
- canonical sorted category JSON; and
- consent timestamp.

It stores no credential, challenge token, signing material, prompt copy, recall
text, memory text, skill body copy beyond the already frozen job snapshot, tool
arguments/results, or attachment content.

For a new remote operation, one existing enqueue transaction writes the user
message, assistant placeholder, run, decision, frozen job, session/run events,
idempotency row, and redacted audit row. Any validation, uniqueness, audit, or
event failure rolls the transaction back. SQLite transactions remain bounded to
the existing enqueue work plus one decision insert and one audit insert.

Session deletion cascades the decision with the run. Existing audit scrubbing
removes run-correlated disclosure metadata when the source session is deleted.
The schema provenance manifest classifies the table as run-owned derived state.
Database backups contain decisions but no credentials or payload copies.

## Runtime enforcement

`AgentJob` carries the frozen `RunEgressDecision`, selected tool names, and
existing frozen skill snapshots. Before provider request assembly or model I/O,
the runtime:

1. classifies the selected provider as local or remote;
2. rejects a remote provider without a decision;
3. rejects a local provider carrying a remote decision;
4. compares provider, model, and canonical endpoint to the actual provider;
5. filters tool definitions to the frozen selected names;
6. confirms every category the execution path may emit is disclosed; and
7. fails the run with non-retryable `egress_decision_invalid` on mismatch.

The runtime never receives signing material and does not authenticate the
challenge. It verifies the orchestrator's already-frozen decision against what
it is about to send.

Provider selection remains an exact map lookup. A missing/failing Ollama
provider cannot consult the OpenAI provider or external-agent resolver. Remote
provider failure cannot change provider, model, or endpoint. Existing
assignment retries may repeat the same frozen operation; a new payload or route
requires a new run decision.

## Endpoint and redirect policy

A shared Go endpoint package is used by orchestrator configuration, external
agent validation, runtime configuration, disclosure generation, and provider
construction.

Credentialed endpoints must use HTTPS unless the hostname is exactly
`localhost` or an IP literal for which `netip.Addr.IsLoopback()` is true. This
allows `127.0.0.0/8` and `::1` development endpoints without treating arbitrary
DNS names or `host.docker.internal` as loopback. No DNS resolution is used to
grant an exception.

Every endpoint must be an absolute HTTP(S) URL with a host and without userinfo,
query, forced query, or fragment. Canonicalization normalizes scheme and host
case, default ports, IP spelling, and trailing slash behavior. The exact
canonical base endpoint is what consent and runtime comparison bind.

Credentialed provider clients reject every redirect before a second request is
made. Same-origin redirects are also rejected: accepting one would make the
prepared endpoint different from the endpoint that receives data, and
HTTPS-to-HTTP redirects would permit downgrade.

## Background and automation behavior

Interactive consent is never a standing capability. A due automation whose
effective session route is remote fails closed before enqueue with typed durable
status `remote_egress_requires_interactive_consent` and a redacted audit reason.
It is not silently skipped, does not create a remote run, and does not inspect
or inherit any previous interactive decision.

Future background egress needs a separate design and explicit unattended
consent model. This task does not pre-authorize it.

## Audit and user-visible notice

Every new remote run records `egress.consent.recorded` atomically. The audit
payload allowlist exposes only:

- destination provider;
- destination endpoint host;
- sorted typed categories;
- decision version; and
- consent timestamp.

Audit never stores or returns the challenge token or nonce, raw fingerprint,
credential reference/value, full request payload, prompt/history/recall/memory,
skill text, tool schema/arguments/results, or attachments.

The same enqueue transaction emits a durable run notice that names the
destination host and disclosed categories. Direct OpenAI and external-agent
runs use the same notice contract.

## Flutter behavior

The provider setting remains a provider preference, not consent. For every
remote send, Flutter first calls `PrepareRemoteEgress`, then displays a modal
with provider/model, endpoint, and all returned categories. Cancel sends
nothing. Confirm returns the exact challenge and category set.

Consent is never stored in secure settings, session state, or provider
preferences. It may remain only in the in-memory retry object for an enqueue
whose outcome is unconfirmed, paired with the same content, provider, and
idempotency key. Editing the draft, changing provider, obtaining a confirmed
pre-enqueue failure, or starting another run discards it and prepares again.
Local Ollama sends do not display a remote dialog.

## Error handling

- malformed or oversized prepare/send input: `INVALID_ARGUMENT`;
- remote send without explicit matching consent: `FAILED_PRECONDITION`;
- expired challenge for a new operation: `FAILED_PRECONDITION`;
- exact expired idempotent replay: original queued/run result;
- conflicting idempotency reuse: `ALREADY_EXISTS`;
- consumed nonce for another operation: `ALREADY_EXISTS`;
- route/tool/skill/category drift after prepare: `FAILED_PRECONDITION`;
- runtime decision mismatch: non-retryable `egress_decision_invalid`;
- remote background route: durable
  `remote_egress_requires_interactive_consent`;
- redirect: non-retryable provider request failure before redirected I/O.

No path falls back to another provider or endpoint.

## Verification strategy

Strict TDD covers:

- deterministic proto generation and compatibility;
- challenge canonicalization, bounds, signature, expiry, and tamper cases;
- side-effect-free preparation;
- direct and routed disclosure categories;
- endpoint classification and redirect refusal;
- migration, schema provenance, restart, deletion, and backup containment;
- exact replay after expiry/config drift;
- conflicting idempotency and concurrent nonce use;
- atomic event/audit/decision enqueue behavior;
- runtime provider/endpoint/category checks and no fallback;
- assignment retries retaining the decision;
- remote automation durable failure;
- audit allowlisting and session scrub behavior; and
- Flutter per-send confirmation, cancellation, changed draft/provider, and
  unconfirmed enqueue retry behavior.

The final change must pass the repository's full verification matrix and the
required independent review sequence before push and PR creation.
